# Architecture

## Layers

```

  app/                 Next.js routes (App Router)
    [lang]/            Every page, once per language (en, es)

      not-found.tsx    A 404 under the banner, in the page's language
```

Dependencies point downward: `app` → `components` → `lib` → `messages`. The
modules in `lib` are pure functions with no React (`rich` builds elements but
renders nothing), so tests can cover them directly.

## Languages

The site speaks English (`en`, the default) and US Spanish (`es`), listed in `LOCALES`
(`lib/i18n.ts`) with their BCP 47 tags (`en-US`, `es-US`) and their names in themselves.
`es-US` keeps American number, money and date formats ("$12,345", "1,234") in Spanish words.

**The language is in the URL.** Every page sits under `app/[lang]`, so each is
prerendered once per language and has an address of its own that search engines can
index; the root layout reads nothing but that segment, never a cookie, so pages stay
static. English keeps its unprefixed URLs and Spanish has `/es`. `proxy.ts` runs on pages
only (not `_next`, the `/auth` route handlers or files with an extension) and:

| Request | Answer |
|---|---|
| `/…` | rewritten to `/en/…`, unless Spanish is remembered: then a GET redirects to `/es/…` (a POST still reaches its action) |
| `/es/…` | served; Spanish is remembered |
| `/en/…` | English is remembered, then a redirect to `/…` |

The memory is the `cs_locale` cookie (a year, `SameSite=Lax`, readable by nothing
sensitive). Server actions and route handlers cannot read the `[lang]` segment, so actions
take their language from it (`actionI18n`): their messages, and where they redirect
(`localePath("/active-lots", locale)`). The OAuth start passes the localized landing path
to the API as `redirect_to`, so the callback lands in the language the sign-in began in.

**Choosing.** The language dialog lists each language as a plain link to the current page
in it, prefixed (`/en/active-lots?…`, `/es/active-lots?…`): a full page load, through the
proxy, which remembers the choice. Signed-in dealers open it from the last item of the
account menu, visitors from the earth button at the right of the banner.

**Words.** `messages/en.ts` holds every word; `messages/es.ts` is typed `Messages`, so a
missing or extra key fails the type check, and `messages.test.ts` checks both have the same
keys and placeholders. Server Components read `getI18n()` (`next/root-params` gives the
segment anywhere in the tree), client components `useI18n()`; the root layout passes the
page's dictionary to `I18nProvider`, so the browser gets one language's words. A client
component outside any provider (a component test) speaks English. Pure modules take the
words or the locale as an argument: the auth schemas are built per language
(`authSchemas(m.auth)`, cached per dictionary), the filter table and the code tables hold
keys into the messages, and every formatter takes the locale for `Intl`. API errors are
worded by their code (`auth.apiErrors`), keeping the API's own message for a code with no
words; the API's field errors (a breached password) arrive in English.

**SEO.** Each page's canonical URL is its own language's, with `hreflang` alternates for
every language and `x-default` on English (`languageAlternates`). The sitemap lists every
page once per language, each naming the others. `llms.txt` is English.

## Lot search and filters

The URL is the lot list's state, with the API's own parameter names (`title=salvage&sort=sale`),
so the server renders every list and a list can be shared. `readQuery` (`lib/lot-filters.ts`)
keeps only the parameters and values `FILTERS` allows, in one order, so equal filters make
equal URLs. The page, for a signed-in dealer:

1. With a search (`q`), asks the API what it names (`/api/lots/interpret`): one lot is a
   redirect to it; a make, model or years are a redirect to those filters (`searched`).
2. With no parameters at all, redirects to the filters kept in the dealer's account
   (`/api/me/lot-preferences`). The filter bar always writes `sort`, so a bare URL only comes
   from elsewhere, such as the banner's link; kept filters that read as nothing do not redirect.
3. Lists the page of lots (`/api/lots`) in the dealer's zone (the `cs_tz` cookie), and
   alongside it asks how many lots were added and updated lately (`/api/lots/activity`, in
   the same zone) for a strip under the banner: "11,821 new lots in the last 3 days",
   "14,769 lots updated today". Each figure is today's once it reaches `ACTIVITY_MIN`
   (1,000), otherwise the last 3 days', otherwise the last 7 days' (`activityWindow` in
   `lib/lots.ts`); today's new lots read "today so far", since the day is not over. An updated lot is one seen before the window, so new lots are not counted
   twice. The list stands without the strip when the API cannot give it.

`LotFilters` turns every change into a new URL (`router.push`, no scroll), so Back undoes a
filter. Its sidebar and bar show every filter between them, so it asks for every filter's option counts
(`/api/lots/counts`, through `lotCountsAction`) once per list, after the list has rendered,
since each filter's counts are a scan of the lots; it drops an answer that arrives after the
filters changed. After each change it stores the filters and
order (not the search's words) through `rememberLotFiltersAction`, unless they equal what the
page read; the API counts how often each parameter is set, and the most used move into the bar.

## Saved lots, searches and alerts

The API keeps what a dealer saves and decides when to tell them (its `docs/architecture.md`,
"Saved lots, saved searches and alerts"); this site shows it and changes it through server
actions, never deciding when an alert goes out.

- A lot's Save, reminders and change alerts are one client component, `LotWatch`, holding what is
  switched on for the lot and updated from each action's answer. The lot page asks for its lot
  (`/api/me/saved-lots/{source}/{lot}`) and the Saved page for all of them; the lot list's cards
  offer no Save, so the list asks for none. Whether a set
  reminder's time has passed is said with the request's clock, passed down, so the server's HTML
  and the browser agree; the dialog reads the browser's clock as it opens.
- A saved search is the lot list's query without its order (`searchQuery`), so equal filters are
  the same search whatever the order, and opening one is a link to the list. The search being
  edited is the list's `saved` parameter, outside `readQuery`'s table: the page looks it up among
  the dealer's searches and `LotFilters` adds it to every URL it makes.
- The inbox renders each entry from its payload, the lots copied into it, so an alert still reads
  after the lot has left the API's database. An entry is unread until the page says otherwise or
  one of its links is followed (`markAlertReadAction`, best effort).
- Actions send the page's language (`actionI18n`) and the browser's zone (the client passes it,
  else `cs_tz`, else UTC); the API keeps them for an account without them (registration sets
  them, so that is a Google or Apple account), until Settings changes them.

## Layout

The site is full width. There is no centered page container: sections span
the viewport with side padding, and only running text is capped at a readable
line length. Auth pages center their form, in a `Card`, in one 28rem column (`max-w-md`).
The top banner shows the logo on the left, linking home, and the account
navigation on the right: "Sign in", "7 days free trial" and the earth button for the
language, or the signed-in dealer's initials in a round button that opens the account
menu (a shadcn `DropdownMenu`: the initials, name and email, then Saved and Alerts below
`lg`, where the main menu is hidden, Settings, Account, Log out and the language). The unread
alerts' count sits on Alerts, and on the initials below `lg`. The navigation is
a client component that asks `/auth/session` (a route handler returning only the
first and last name, the email and how many alerts are unread, asked of the API together) after
every navigation, so the pages themselves stay static and signing in or out,
which both redirect, updates it. On `/register` and `/login` it renders only the
earth button, so the banner is the logo and the language.

## Colours and assets

The brand, CarBidInsight, appears as the banner's logo (`public/logo.png`,
whose navy and green are its own), which links home, and the black-and-green CBi
favicon (`src/app/favicon.ico`). The favicon contains compressed 16, 32 and 48px
images on white, cropped and resized from the supplied logo. Next.js automatically
links it on every page in both languages; the language proxy skips its file URL.
There is no touch icon, manifest or share image yet, and no structured data. Page titles stand
alone. The interface is built from shadcn/ui components (`src/components/ui`) and
uses black, grey and white only, through shadcn's neutral theme tokens in
`src/app/globals.css` (`--background`, `--foreground`, `--primary`, `--muted`,
`--muted-foreground`, `--border`, …), Work Sans (loaded with `next/font/google` in
the root layout, the system font stack behind it), and no dark mode. The same file
sets the radius scale and the border and focus colours, on top of Tailwind's spacing
and type scales; `AGENTS.md` lists them, and `src/components/ui/design-system.test.ts`
fails on a value off them. The look is flat: borders separate, and only floating
surfaces (popovers, menus, the sheet, the dialog) have a shadow. There is no
error colour: `--destructive` is the text colour, so errors read as bold text. The lot page's deal-breaker
badges and sale countdown are the one exception: green, amber and red
(`--good`, `--warn`, `--bad`), always with an icon and words as well. Add branding once a name and a
design are settled.

## Route registry

`src/lib/routes.ts` lists every indexable page with its sitemap priority, and
whether it appears in `llms.txt`; each language's `pages` (`src/messages`) holds its
title and description, typed by the registry's paths. Pages read their metadata
through `metadataForRoute(path)`, in their `generateMetadata`. `routes.test.ts`
fails if a static `page.tsx` under `src/app/[lang]` is missing from the registry,
if a page's words are missing, or if a title or description is outside snippet
lengths in any language. The builders take an optional route list, and tests pass
them `src/lib/seo/fixtures.ts`.

## SEO module

- **Site URL.** `resolveSiteUrl` uses `NEXT_PUBLIC_SITE_URL`, falling back to
  `http://localhost:3000`. Only a `NEXT_PUBLIC_` variable is used, because
  Next.js inlines those into client bundles too, so server and browser always
  agree on the value. Every absolute URL goes through `absoluteUrl()`.
- **Metadata.** `buildMetadata` sets the title, description, canonical URL (the
  page's own language), `hreflang` alternates, Open Graph (with its locale),
  Twitter card and robots directives. There is no share image yet,
  so the Twitter card is a plain `summary`.
- **Structured data.** None: every schema.org type worth emitting here needs a
  brand name, and there is none yet. The builders come back with the brand.
- **AI crawlers.** `robots.txt` is a single `User-Agent: *` / `Allow: /` rule,
  which admits every crawler, AI search and assistant bots (GPTBot, ClaudeBot,
  PerplexityBot, Google-Extended and others) included. `/llms.txt` summarizes
  the site and links its key pages.
- **Rendering.** Pages should be prerendered to static HTML, so crawlers that
  don't run JavaScript still see the full content.

## Accounts

Accounts live in the API (`../cars-secrets-api`, see its `docs/architecture.md`). This
site never stores credentials or talks to a database. The API client defaults to
`http://localhost:8001`; `API_URL` overrides it for other environments. Start the local
API with `uv run uvicorn app.main:app_factory --factory --reload --port 8001` from
`../cars-secrets-api`. Server actions in
`src/app/[lang]/(auth)/actions.ts` post to the API through `src/lib/api.ts`, which adds the
visitor's address with the shared `API_INTERNAL_KEY` so the API rate-limits visitors and
not this server.

Forms use React Hook Form and the Zod schemas in `src/lib/auth-schemas.ts`. Errors show
when a field loses focus (`mode: "onTouched"`) and on submit, before any request. Every
input carries the same limit as its schema, so nothing over-long is typed in the first
place. The server action parses
the same schema again, calls the API and returns field errors, which `showServerErrors`
puts on the matching inputs without clearing the form. The email typed in one auth form
is remembered for the tab once it is a complete address, and prefilled in the others;
sign in then focuses the password. Entering a confirmation code or signing out forgets it.

- **Register**: the form posts names, email, the phone (one control holding the country
  picker and the number, joined into `+<calling code><digits>`; the API normalizes to
  E.164), password and the Turnstile token, with the page's language and the browser's zone
  (`registerAction(values, browserZone())`, else `cs_tz`, else UTC): the API keeps them as the
  dealer's settings, so every email is in that language from the code on. Agreeing to the Terms of Use and Privacy
  Policy is what the submit button does ("Agree and register", with a sentence saying so),
  so there is no checkbox to validate and the action sends `accept_terms: true` itself. The country defaults to
  the region of the browser's first language (`countryFromLanguages`), and on mount the
  form replaces it with what the browser itself knows (`countryFromBrowser`: its time
  zone first, its languages second). The country's example number is the placeholder, the
  shape the digits are formatted into as they are typed and the ceiling they stop at
  (`formatNational`), and the lengths the number is checked against
  (`isValidNationalNumber`). The password field
  ticks off `PASSWORD_RULES` live — 8 characters, a letter, a number and a special
  character — from the first focus on the input onwards, and warns about Caps Lock. The
  same list is what the schema validates, and the API applies it too. The form also renders the Google and Apple
  buttons, so the code step that replaces it on success replaces them too; "Use a
  different email" goes back to the form with its values.
- **Confirm**: the API mails a six-digit code (valid 10 minutes). `VerifyEmailForm` asks
  for it in one field (`autocomplete="one-time-code"`, numeric keyboard), keeps only the
  digits of whatever is typed or pasted (`codeDigits`) and submits on the sixth. A right
  code signs the dealer in: `verifyEmailAction` sets the session and redirects to
  `/active-lots`. A wrong one clears the field and says so on it. "Send a new code" appears
  after 60 seconds, the API's own minimum between codes. The step follows registration,
  a sign-in on an unconfirmed address, and `/verify-email`, which asks for the address
  first (prefilled from the tab's remembered one).
- **Sign in**: on success the API returns a token, which becomes the `cs_session`
  cookie (30 days with "remember me", browser session otherwise), and the visitor lands
  on `/active-lots`. The choice itself is kept in the `cs_remember` cookie, which
  sign-out leaves, so the box comes back ticked after a sign-in that had it. When the API answers `captcha_required`, the form shows the Turnstile
  widget. A wrong password clears the password (not the email) and offers a reset link.
  A right password on an unconfirmed address makes the API mail a code, and the form
  turns into the code step, keeping "remember me" for the session it opens.
- **Forgot / reset**: `/forgot-password` asks for the email; the emailed link opens
  `/reset-password?token=…` (under `/es` for a dealer whose emails are in Spanish), which sets
  the new password. The API then signs out every session of that user and emails a "password
  changed" notice.
- **Google / Apple**: the buttons call `socialLoginAction`, which gets the provider URL
  and a `state` from the API, stores the state in the `cs_oauth_state` cookie and
  redirects. The provider returns to `/auth/callback/{provider}`; the route handler
  compares the state with the cookie, asks the API to finish the handshake, sets the
  session cookie and lands on `/active-lots`.

The register page builds the country list on the server from `dial-codes.ts` (generated
from the phonenumbers metadata the API uses), names from `Intl.DisplayNames` and flags
from the regional indicator symbols, and passes it to the form, so no flag images ship
and server and browser agree on the names.
To regenerate `dial-codes.ts`, run the snippet in its header against the API's
environment. `phone-formats.ts` carries the example number shown as the placeholder,
the national lengths the number is validated against and the trunk prefix, from the
same metadata; the snippet in its header regenerates it the same way.

## Lot price prediction

The lot page reads `predicted_final_price` from the existing authenticated lot API response
and renders it as "Likely final bid" in the lot's currency. It is a single model estimate,
not a range; null displays "Not available". The ingest model currently trains on generated
sold prices, so this is an estimate rather than a confirmed sale price. No similar-sales
count is claimed. `DealCalculator` still uses explicitly labeled sample costs and profit.
